# Calindra Strike

Browser FPS with Counter-Strike 1.6 style gameplay for the Calindra office. Authoritative Node.js WebSocket server plus a Vite + Three.js client. See `README.md` for gameplay, server settings and hosting.

## Layout

npm workspaces, TypeScript (ESM), Node >= 22.

| Path | Purpose |
| --- | --- |
| `shared/` | Deterministic code used by both sides: movement (`sim.ts`, `physics.ts`), weapons, maps, protocol |
| `server/` | WebSocket server, match lifecycle (`game.ts`), bots (`bot.ts`, `nav.ts`), rate limiting, env config |
| `client/` | Rendering, prediction, input, HUD and menus |
| `tools/` | Dev bots (`bots.ts`) and perf bench (`bench.ts`) |

## Commands

```bash
npm install
node --run dev:server     # game server on :7350
node --run dev:client     # Vite dev server
node --run test           # node --test (shared + server tests)
node --run typecheck      # tsc for shared (+ tests), server, client and tools
node --run build:client
node --run start:server   # production-style start, no build step
node --run bots           # dev bots against a running server
node --run bench          # tick budget with bots
```

Run `node --run test` and `node --run typecheck` before finishing a change.

To see a change working in the real app, use the project skill `.claude/skills/verify-calindra-strike` (isolated server + client, doctor, dev bots, feature map). The MCP browser has no WebGL, so the in-game 3D view and HUD cannot be verified there; the skill says how to prove the server side instead.

## Debug mode

Enter the Konami code (`↑ ↑ ↓ ↓ ← → ← → B A`) in the lobby outside a text field. The **modo** row switches between the first-person weapon viewer and a free-flight scenario explorer. Both run without joining a match.

- **Every weapon goes in it.** Each entry of `WEAPONS`, with each of its skins, must be selectable in the viewer and by its URL. A new weapon, skin or weapon-specific state is not finished until it can be looked at there. `client/test/debug-viewer.test.ts` checks that every weapon is reachable by its tag.
- **Test weapons there.** A change to a weapon model, skin, reload or fire animation, or to where the gun sits in the view, is checked in the viewer before it is called done. Unit tests do not show what the player sees.
- **Opening it.** On the lobby screen (not while typing in a field) press the Konami code, `↑ ↑ ↓ ↓ ← → ← → B A`. Harnesses open it by URL on the client: `?viewer&weapon=azt&skin=carrapeta&aim=1&reload=0.35`. `weapon` is the weapon's tag, ignoring case and accents. `skin` is `standard` (default) or `carrapeta`. `aim=1` holds the aim-down-sights pose (the AWP has none, and its scope cannot be opened in the viewer) and `reload` (0 to 1) holds that point of the reload. Every parameter but `viewer` is optional.
- **Harness recipe.** The title becomes `viewer:ready` after the first frame, or `viewer:error` without WebGL. The MCP browser has no WebGL, so use headless Chromium with software rendering: `chromium --headless=new --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist --window-size=1400,850 --virtual-time-budget=30000 --screenshot=out.png 'http://127.0.0.1:5273/?viewer&weapon=awp'` (the port is the client's own: 5273 in the verification sandbox; `--dump-dom` instead of `--screenshot` shows the title). Open the picture and look at it. A still frame shows geometry, colour and framing, not motion: hold poses with `reload`, and ask the user to judge how an animation moves.
- **Controls.** Pick any weapon, skin and graphics tier, fire once or hold the trigger at the weapon's cadence, play a reload (speed 0.25× to 2×, loop) or drag the reload slider to hold one pose, turn the walking bob on, change the field of view, and move, rotate and scale the gun.
- **Tuning an angle.** `copiar para o código` copies the current placement as one line to paste into `client/src/game/render/weapon-placement.ts`, the table the game reads. `restaurar` goes back to the weapon's own placement.
- **Resource ownership.** `ViewModel` disposes the outgoing weapon’s owned resources on swap and preserves shared geometry, materials and textures. Register shared resources from `buildWeapon` in `SHARED_WEAPON_RESOURCES`.
- **Scenario explorer.** `scenario-explorer.ts` builds the selected map with `buildWorld` and starts at its first benchmark tour point. Click the canvas to lock the mouse and hide the panel. WASD moves, Space climbs, Ctrl descends and Shift speeds up. Esc brings back the panel, with map, graphics, FOV, reset position and first-person weapon controls. The explorer uses the map's daylight look and skips the day cycle and ray-traced contact shadow pass.
- **Fullscreen.** Both views offer **maximizar janela** when the browser supports fullscreen. The debug stage resizes on `fullscreenchange` and the button changes to **sair da tela cheia**. Leaving debug exits stage fullscreen and removes the listener.
- **Performance HUD.** F3 and **mostrar FPS** toggle the overlay in both modes. `perf-hud.ts` samples frame cadence, CPU render submission, GPU timer queries when supported, JS heap when available, and renderer draw and resource counts. The GPU percentage measures the share of frame time. WebGL cannot read device-wide GPU utilisation or VRAM usage.
- **Where it lives.** `client/src/main.ts` uses the matcher in `client/src/easter-egg.ts` and dynamically imports `client/src/debug/weapon-viewer.ts` only after the code is entered. The panel uses `client/src/ui/controls.ts`, shared with the pause menu. The pure, Node-tested logic lives in `weapon-debug.ts` (reload and fire), `fly-camera.ts` (flight and mouse look) and `perf-stats.ts` (frame statistics and formatting). The explorer and HUD run only in debug mode and need no `QualityProfile` column.
- **Needs WebGL.** Without it the viewer only shows a notice and the way back to the lobby, which is what the MCP browser gets. An agent cannot judge the animation there: ask the user to look, or render frames in software from `ViewModel` (stub `document.createElement('canvas')`, then rasterize `view.scene` with `view.camera`), which shows geometry and framing but not motion.
- **When to use it.** Any change to a weapon model, a reload or fire animation, or where the gun sits in the view. Put new weapon-specific controls in the viewer, not in the game.

## Node standard library first

Server, shared code, tests and tools use only what Node (>= 24) ships, plus the exceptions below. Before adding a package or a hand-rolled helper, check whether Node already has it.

- **Run TypeScript natively.** `node file.ts` strips types, there is no `tsx`, bundler or build step for the server. Only erasable syntax is allowed (`erasableSyntaxOnly` is on for shared, server and tools): no `enum`, `namespace` or constructor parameter properties (`constructor(private x: T)`); declare the field and assign it. Keep `.ts` extensions in relative imports.
- **Tests use `node:test` and `node:assert/strict`**, not vitest/jest. Run with `node --run test` (`node --test`). Use `assert.partialDeepStrictEqual` instead of `toMatchObject`, and restore `process.env` in `afterEach` when a test changes it. Shared float helpers live in `shared/test/helpers.ts`.
- **Prefer built-ins:** `node:`-prefixed imports, `util.parseArgs` for CLI args, `--env-file-if-exists` for `.env`, `node --watch` for dev reload, global `fetch`, `WebSocket` (client), `performance.now()`, `structuredClone`, `crypto.randomUUID()`, `AbortSignal.timeout()`, `timingSafeEqual`, `Array#toSorted`, `Object.groupBy`, `Set` methods.
- **Allowed exceptions** (justify any new one in the PR):
  - `ws`: Node has a WebSocket client but no server. It is the only runtime dependency of the server.
  - `typescript` and `@types/*`: type checking only, never executed at runtime.
  - `vite`, `three` and the `@fontsource` packages: browser client bundling and rendering, outside the Node std scope.
- The Docker image copies the sources and runs `server/src/index.ts` directly; keep it free of a build stage.

## Design: clean architecture, clean code, patterns

Prefer these when writing or changing code. Apply them to the code you touch, do not rewrite unrelated files for style.

**Dependency rule.** Dependencies point inward only:

```
client ─┐
        ├─► shared   (domain: simulation, weapons, maps, protocol; imports nothing else)
server ─┘
tools ──► server, shared
```

- `shared/` is the domain core. It must not import from `server/` or `client/`, and must not touch Node or DOM APIs, sockets, timers or `process`.
- `server/` and `client/` never import each other. Anything both need goes into `shared/`.
- Keep I/O at the edges. `Game` (`server/src/game.ts`) is the application layer: it takes plain callbacks and options (`send`, `random`, config) and knows nothing about `ws` or `http`. `server/src/index.ts` is the adapter and composition root: HTTP, WebSocket, origin checks, rate limits, signal handling, and wiring `Config` into `Game`. New transport concerns go there, new game rules go in `Game` or `shared/`.
- Inject what makes code non-deterministic or hard to test (random source, clock, config, send callbacks) through constructors or options, as `GameOptions.random` already does, instead of reaching for globals. Read `process.env` only in `server/src/config.ts`.
- Parse and validate at the boundary (`parseClientMessage`, `loadConfig`), then pass typed values inward. Inner code does not re-validate.

**Clean code.**
- Names say what and why, not how. A function does one thing at one level of abstraction; split `Game` methods that mix rules, scoring and broadcasting rather than adding another branch.
- No magic numbers: tuning values go in `shared/src/constants.ts` or `weapons.ts` with a unit in the name or a comment (ms, units/s).
- Make illegal states unrepresentable: discriminated unions for messages and phases, `readonly` fields, `as const` tables. Avoid `any`, non-null `!` and type assertions outside tests.
- Early returns over deep nesting; no flag arguments; no dead code or commented-out code; comments explain why, not what.
- Small, pure functions in `shared/` first (they are trivially testable), side effects in thin wrappers. New behavior comes with a test next to the layer it lives in.

**Design patterns: use them when they remove a real problem, not by default.**
- *Strategy / table-driven* over long `switch` or `if` chains on mode, weapon or map (game modes, weapon definitions and map registry are already data-driven, extend those tables).
- *Factory / builder* for constructing maps and entities (`MapBuilder`), keeping construction separate from use.
- *Adapter / ports* around external things (sockets, clock, randomness) so the core stays testable with fakes.
- *Observer / callbacks* for events leaving the core (kills, loot, phase changes) instead of the core calling transport code.
- *State machine* for match phases (warmup, live, podium): explicit states and transitions, no scattered booleans.
- Prefer composition over inheritance. Do not add layers, interfaces or abstract classes with a single implementation and no seam to test against.

## Conventions and gotchas

- **Stances and movement.** A player's pose is `PlayerState.stance` (`STANCE.STAND|CROUCH|PRONE`, table `STANCES` in `shared/src/stance.ts`: hull, eye, speed, hitboxes, bot aim heights); read the table, do not branch on the stance. Sprint, stamina (a sprint already running that is slower than `STAMINA_DRAIN_MIN_SPEED`, a wall in front or standing still, neither drains nor refills; the start of a sprint always drains), slide, lean and the prone lock are advanced per command in `playerMove` (`shared/src/sim.ts`) from the button bits `SPRINT`, `LEAN_LEFT`, `LEAN_RIGHT`, `PRONE`; tuning is under `SPRINT_`, `STAMINA_`, `SLIDE_`, `LEAN_`, `PRONE_` in `constants.ts`. A lean moves the eye and the shot origin (`eyePosition`) and the head and body hitboxes (`hitboxes(x, y, z, stance, lean, yaw)`), so the server keeps stance, lean and yaw in its lag compensation history. Remote rows carry `RF_PRONE`, `RF_SPRINT`, `RF_SLIDE` and the lean at index 8 (`stanceFromFlags`, `leanOfRow`). The client pants while `winded` (`Panting` in `client/src/game/panting.ts`, `Sfx.breath`), a sound for the local player only. Bots never sprint, slide, lean or lie down; MCP agents press them with the `sprint`, `slide`, `lean` and `prone` tools (`ActionOverlay` in `tools/mcp/actions.ts`; its `slideBlocker` mirrors `tryStartSlide`, and `tools/test/actions.test.ts` runs the two against the sim so they cannot drift).

- **Aim down sights (ADS).** The `ads` definition in `shared/src/weapons.ts` supplies FOV, speed and spread tuning. The sim evaluates held `ATTACK2` for movement and again after weapon timers advance. Aiming slows movement, tightens spread, ends sprinting and drops during reload and deploy. The self snapshot carries `aiming` and remote rows use `RF_AIM`. `RF_ZOOM` marks the AWP scope. Bots only auto-scope the AWP. MCP `zoom(1)` holds ADS and `zoom(0)` releases it, with objective use taking priority and weapon changes clearing the latch. `you.aiming` reports effective ADS. The AWP keeps levels 0 to 2 and the hammer rejects zoom. Its right button is the heavy swing, MCP `fire` with `heavy: true`: `ActionOverlay` holds `ATTACK2`, drops the pilot's `ATTACK` (the sim swings heavy only with it up) and cancels the swing on a switch away from the hammer (queued, unacknowledged or shown by the snapshot). A switch made by the server alone, such as an airdrop, is only seen when its snapshot arrives.

- **Remappable controls.** Add the action id and one row to `ACTIONS` in `client/src/game/bindings.ts`. The `Record<ActionId, Action>` requires a row for each id. Set a `BTN` bit or weapon request there for input handling, or handle client-only actions in `ClientGame`. `Settings.bindings` stores only overrides. The lobby (behind its **controles** button, as a page of its own), pause menu and weapon viewer share `controlsList`, which resolves the same bindings as `Input`. List fixed contextual shortcuts in `controls-list.ts`.

- **Radio lines** are the `RADIO_MENUS` table in `shared/src/radio.ts`; append lines and menus to preserve their positional wire ids. Each menu holds up to nine lines. Calindra uses B and Calindra 2 uses N. See "Radio lines" in `README.md`.

- **Kill feed weapon icons** are baked at runtime from `buildWeapon` in `client/src/game/render/weapon-icons.ts` (side view, flat light tones, one icon per entry of `WEAPONS`), so a new weapon gets its icon with its model and needs no extra art. A kill by a weapon without a model fails `client/test/weapon-icons.test.ts`. Baking uses a throwaway WebGL renderer on first kill and returns null without WebGL, where the feed shows the text tag.

- **Sound packs** live in `client/src/game/sound-packs/`: export a SoundPack and register it in SOUND_PACKS; omitted voices use classic. Runtime-loaded mods are not supported.

- **Hora de almoçar** rules are pure in `shared/src/lunch.ts` (`stepLunch`, tuning in `constants.ts` under `LUNCH_`). The server runs them in `Game.updateLunch`, reusing `attackers` from debug defusion for the side that leads, and the client draws colleagues with `ColleaguesView` (`client/src/game/render/colleagues.ts`, the player `Avatar` in white). A map plays the mode only when it lists `restaurants` (`MapBuilder.restaurant`), checked by `modeFitsMap` when the rotation is built. MCP agents read it from `get_state.lunch` (built in `describeLunch` in `tools/mcp/view.ts` from the snapshot rows, decoded by `colleagueFromRow`), `hunt` plays it through the same `pickLunchGoal` as the server bots, and `use` calls the colleagues in reach. `LunchRound.target` indexes `MapDef.restaurants` (each has a `name`, `b.restaurant(x, y, z, name)`); the server draws it per round, sends it as the third element of `snap.lu`, and only that restaurant seats a colleague. Bots and the MCP pilot get just the target in `restaurants`. A round is a `rush` hour with chance `LUNCH_RUSH_CHANCE` (0.4, tuning): its clock runs `LUNCH_RUSH_SPEED` (2) times faster, so it lasts `lunchRoundTicks(true)`. The server draws it per round after the target and sends it as the fourth element of `snap.lu` (no protocol bump: older readers ignore it). The client marks the target restaurant with `LunchTargetView` (`client/src/game/render/lunch-target.ts`: beam, ring of `LUNCH_SEAT_RADIUS_UNITS` and a floating name, red and faster in a rush) and announces each round once in `ClientGame.announceLunchRound` (`lunchAnnouncement`): a feed line plus the centred `Hud.announceLunch` banner, which draws the restaurant's logo with `signCanvas(place.brand)` (`store-signs.ts`; `b.restaurant(x, y, z, brand)` takes a `FoodBrand`, so a restaurant always has a sign drawing) and adds the rush call. `followersOf` counts the colleagues whose `leader` is the local player; `Hud.setLunchFollowers` shows the chip only above zero. Both are visual only: MCP agents already read `leader` per colleague in `get_state.lunch`.
  The target beacon turns blue with a second outer ring and the caption "IMPEÇA O ALMOÇO" for the defenders (`LunchTarget.side`), so the side reads without the chip.
  The HUD reuses the chip rendered for `bombRole` to show the lunch objective from `lunchRole`, including the rush call for attackers.

- **Carrapeta Dourada.** The rules live in `shared/src/carrapeta.ts` and `Game` owns holder selection, drops, scoring and Batata Quente. Tuning is in `constants.ts` under `CARRAPETA_` and `BATATA_`, with the drop redraw delay configurable via `CARRAPETA_PICKUP_TIMEOUT_SECONDS`. A new holder gets `MAX_HEALTH` health and `CARRAPETA_ARMOR` (200) armour, `Game.holdsCarrapeta` keeps them from airdrops (bots skip them too), supply stands never lower the armour, and losing it caps armour at `MAX_ARMOR`. A holder loses it after `CARRAPETA_MAX_HOLD_SECONDS` (`holdExpired`). `Game.updateCarrapeta` drops it and waits `CARRAPETA_REDRAW_WAIT_SECONDS` (5, tuning value) with a countdown on the status strip. The redraw leaves that player out while anyone else is landed. Every match schedules `BATATA_PER_MATCH` frenzies, one per slice of the window (`frenzyAtTicks`, queued in `Game.frenzyQueue`). The Azeitadora is `WEAPON.MGL` (it has an `ads` like the other guns; its model is built in `weapons3d.ts` with a `rig.drum`, and `DrumView` plus the pure `drum-anim.ts` turn the drum one chamber per round and fly the fired and dumped rounds, while the reload pose carries `drumTurn`, `drumFill` and `drumDump`; `ICONS.carrapeta` is the golden top drawing used by the banner); `infiniteMgl` keeps the holder's reserve infinite and `halvedAmmo` changes effective capacity during the frenzy, and `halveVitals` halves the holder's health and armour when it starts or when a new holder takes it mid-frenzy (never restored). `blast.ts` supplies radial damage. `carrapetaEnemies(state, a, b)` is the one combat rule (server hitscan, bots and MCP all read it): with a holder only pairs that include the holder can hurt each other, with nobody holding it everyone can, and a death then waits `CARRAPETA_LOOSE_RESPAWN_EXTRA_TICKS` longer (the kill event carries `wait` so the client countdown matches). Snapshots carry `ca`, and Carrapeta score rows append points at index 6. The `carrapeta`, `frenzy` and `blast` events report possession changes, Batata Quente transitions and explosions. MCP `get_state.carrapeta` exposes the holder, drop, timers and points, and `hunt` uses the same objective and enemy rules as the server bots. `weaponSkin` in `weapons3d.ts` selects gold and walnut in Carrapeta Dourada matches and dark materials with lime accents by default: only the holder's guns are gilded (`weaponSkin(mode, holdsCarrapeta)` returns `carrapeta` for the holder and `toy` for everyone else in the match, read per player by `ClientGame.skinOf`): the Azeitadora has its own finish, the holder's other guns go through the `GILDED` material table, and every player's hammer is a red and yellow squeaky toy hammer (`toyHammer`); `client/test/weapon-skin.test.ts` pins all three. Dev bots play through `carrapetaBrain` (`tools/carrapeta-goals.ts`) and share the enemy rule.

- **Day cycle.** The phase (`day`, `afternoon`, `night`) is a pure function of the server clock: `dayCycleAt(serverMs)` in `shared/src/day-cycle.ts`, tuning in `constants.ts` under `DAY_`, no protocol message (the client already tracks `serverNow()`). Each phase's slot ends with a blend into the next. The look is `client/src/game/render/day-look.ts`: `buildLooks(theme)` returns one `DayLook` per phase, the day is the map's `MapTheme` untouched and the others come from the `PHASE_GRADES` table (colours move toward a tint, scales, sun turn and height, exposure, stars, glow), unless the theme sets `phases.afternoon` or `phases.night` to override fields. `ClientGame.updateDayLight` mixes two looks with `lookAt` and hands the result to `WorldView.applyLook` (sky shader uniforms and stars, hemisphere and sun, fog, emissive materials, light halos, distant silhouettes), `ViewModel.setLighting` (the gun) and the renderer exposure. It only writes values: no new lights, passes or per-frame allocations, so it is on every tier, and a settled phase costs nothing. Night must stay readable (players clearly visible at range, fog distance unchanged, no near-black interiors): `day-look.test.ts` asserts a floor on the light that reaches a player, so check it when retuning `PHASE_GRADES`. The benchmark builds the world and never applies a look, so it measures day. A new emissive material that should glow more at night only needs to be a `MeshStandardMaterial` with an emissive colour in `buildWorld`'s material table. MCP agents read the phase from `get_state.timeOfDay`; it is a look only.

- **Store signs** are the `STORE_BRANDS` table in `shared/src/maps/brands.ts` (parody names, `food`, `shop`, `boutique` or `floor`; floor signs name the levels over the lift doorways). A map puts one up with `b.deco(..., brandMat('kfg'))` on a 2:1 panel, and the client draws it from the `SIGNS` table in `client/src/game/render/store-signs.ts`, a `Record<StoreBrand, ...>`, so a brand without a drawing fails the typecheck. Sign mats count as plaster for impacts.

- **Shared code is deterministic.** Client prediction and the server run the same simulation from `shared/`. Do not add randomness, wall-clock time or environment-specific behavior there; use the seeded spread helpers. A change to movement or weapons affects both sides and needs a test in `shared/test/`.
- **Protocol changes:** edit `shared/src/protocol.ts`, the server handler in `server/src/index.ts` / `game.ts`, and the client message handling in `client/src/game/client.ts` (`net.ts` is transport only, the handshake is in `client/src/main.ts`). Bump `PROTOCOL_VERSION` in `shared/src/constants.ts` for incompatible changes. Keep message validation strict, the server treats every client message as untrusted.
- **Server is authoritative.** Hit detection is lag-compensated hitscan (rewind up to 250 ms) at a 60 Hz tick. Never trust client-reported damage or positions.
- **Surfaces and impact sounds.** Every map `Mat` maps to a `Surface` in `shared/src/surface.ts` (the client plays it, the MCP reports it). A surface also needs a sound layer set in `client/src/game/surface-sound.ts` and a spark look in `client/src/game/surface.ts`; both are `Record<Surface, ...>`, so a missing entry fails the typecheck. Coloured sparks and glints are the high tier only (`fx.sparkle` in `quality.ts`), the sounds are on every tier. `CollisionWorld.trace` returns the `mat` it hit. Bullets fly through shoot-through glass and water, so `trace` skips them; `CollisionWorld.tracePane` finds the first visible pane whose surface is `glass` up to where the round stops, and the client plays a second impact there.
- **MCP senses.** `get_state.sounds` is built in `tools/mcp/session.ts` from the server's shot and hit events plus the agent's own shots (the server never sends a player their own, so they come from the magazine dropping). Loudness is `heardIntensity` in `shared/src/hearing.ts`, the same curve as the browser's positional audio. `aim` and `fire` are an overlay on the pilot's command in `tools/mcp/actions.ts`.
- **Props and scenery.** A `MapProp` (`shared/src/maps/types.ts`) is scenery the client draws from a model and may animate: ceiling fans, mannequins, clothes racks, escalators, the fountain, vents. Props are never solid and never part of collision or the nav grid; whatever must block stays a `Box`. Author them with `b.prop(...)` (or `b.escalator(...)`, which keeps the stair boxes for collision but hides them) so the 180 degree mirror turns them too. An escalator prop has `travel: 'up' | 'down'` (`MapBuilder.escalator` requires it, the mirror keeps it, `escalatorPhase` runs the steps backwards for `'down'`): its stair boxes and the nav grid are the same as for any staircase, and its steps also carry a rider: `escalatorDrift` (`shared/src/escalator.ts`) returns the drift (`ESCALATOR_SPEED_UNITS`, 30 units per second along the incline, up for `up`, down for `down`) for a grounded player whose centre is over the incline and whose feet are on its treads, and `playerMove` adds it to the walk (`walkMove` drift) without changing the velocity, so the server and the prediction agree and the drawn steps use the same speed. The client keeps one builder per kind in `PROP_BUILDERS` (`client/src/game/render/props.ts`), a `{ [K in PropKind]: ... }` table, so a kind without a drawing fails the typecheck. Static models are merged into one mesh and moving parts are instanced, so a kind costs a few draw calls, not one per object. The pure motion rules (escalator steps, fountain drops, vapour) live in `prop-motion.ts` and are tested. `Box.tint` (`b.deco(..., mat, tint)`) multiplies a material's colour at no extra draw call; use it instead of adding materials. Kitchens and store interiors are authored with `Room` (`room.ts`), a depth-from-the-back-wall frame, in `shopping-kitchens.ts` and `shopping-stores.ts`, as `Record<FoodBrand | ShopBrand, ...>` tables. A food court kitchen is a visible set plus one solid invisible `clip` box, so it can be seen over the counter and never entered.
- **Store staff.** A `staff` prop (`MapProp`, `Room.staff(x, z, gaze, role, uniform)`) is an employee drawn as the store mannequin in a uniform: `cashier` at a till, `cook` at a kitchen station, `server` at the food court window. `STAFF_UNIFORMS` in `shared/src/maps/staff.ts` holds one row per brand, so a brand without one fails the typecheck. Staff are scenery and only ever stand where players cannot walk: inside a food court kitchen's `clip` box, or in a boutique's till cubby, which the till closes with solid side panels and the back wall. `shared/test/staff.test.ts` fails a staff member that is not inside a kitchen or closed in on all four sides within 60 units, or that overlaps a solid box or any furniture or equipment box. They are not solid, not in the nav grid, not on the wire and not hittable, and bots and players never target them. The client draws each body into the static mesh and instances the two arms (`StaffArms`, `client/src/game/render/staff.ts`), posed by `staffArmSwing` in `prop-motion.ts`. The `staffMotion` column of `QualityProfile` (high and low) moves the arms; performance keeps them in their resting pose, one extra draw call per arm mesh. Store counters (`counter()` in `shopping-stores.ts`) are look only, so the clothing and shop floors have no staff: a figure behind a walk-through counter would stand in walkable space. Make the counter solid before adding staff there. Tills stand 50 units, above the 45 unit jump, so nobody climbs onto one from the floor; a player standing on a 38 unit display can still reach one and drop into its cubby, the one edge left.
- **Air conditioning ducts.** `b.duct(...)` / `Room.duct(...)` author a duct: a non-solid `metal` box flagged `duct` that stops bullets (so it rings as metal) but is walked through. `onDuct(map, x, y, z)` (`shared/src/maps/duct.ts`) tells the client a hit landed on one, and `GunFx.leak` lets air hiss out of the hole for `DUCT_LEAK_SECONDS` (2) through the barrel smoke pool (`DuctLeaks` in `client/src/game/render/duct-leak.ts`), only where `QualityProfile.fx.ductLeak` is on (high). Keep a duct clear of the kitchen hoods (the food court duct runs above them, under the ceiling) and hang a free-standing duct from a riser. `shared/test/duct.test.ts` pins it.

- **Glass lifts.** `MapDef.lifts` (`shared/src/lift.ts`, authored with `b.lift(minX, minZ, maxX, maxZ, stops, doors)`, turned with the half) is one cab per shaft that everybody shares, a pure function of the server clock: `liftCab(lift, tick)` goes up through every stop and back down, waiting `LIFT_STOP_WAIT_TICKS` (90, a tuning value) at each, at `LIFT_SPEED_UNITS`, with no state and no buttons. `rideLift` in `shared/src/sim.ts` carries a rider whose centre is in the footprint and whose feet are within `LIFT_CARRY_UNITS` behind the cab floor in its direction of travel (`carriedBy`), and sets their height to the cab's (a cab waiting at a stop carries riders whose feet are on its floor too, because the shaft has no floor of its own at the upper stops); anyone else in the shaft falls to the ground. Each doorway is a `LiftDoor` (the wall slab across it, authored in `liftShaft` in `shopping-top.ts`) that `CollisionWorld` keeps as a solid unless `liftDoorOpen` (the cab waits at its stop): setting `liftTick` shuts or opens them, in fixed slots at the end of the solids array, so nobody steps into an empty shaft. The doors shut `LIFT_DOOR_CLOSE_TICKS` (12) before the cab leaves, so whoever is mid-doorway is already on the cab when it sets off, and `rideLift` never drags a rider at the doorway edge down into the floor slab (the drawn doors follow the same window). A player who stands overlapping a shut door slab can still walk in (a box the hull already overlaps is ignored), a rare edge that ends in a fall to the ground. Code that maps the walkable space (`NavGrid`) builds inside `world.withDoorsOpen`. Jumping is off inside a shaft. The cab clock is `CollisionWorld.liftTick`: whoever applies a command sets it with `liftClockTick(cmd.interp, INTERP_DELAY_MS, serverTick)`, the command's own clock (the client's render time plus the interpolation delay) when within `LIFT_CLOCK_SLACK_TICKS` of the server tick, else the server's. The server (`Game`) and the client prediction (`ClientGame.predict`) do that, so both run the same tick for the same command, with no protocol change. A test or tool that runs commands itself sets `world.liftTick` per tick. The shaft is glass boxes with a doorway per stop (`LIFT_DOOR_HEIGHT_UNITS` high) cut into the wall, and the cab is only drawn: the `lift` `MapProp` (`buildLifts` in `client/src/game/render/props.ts`, door easing in `prop-motion.ts`) draws the one cab at `liftCab(stops, serverTick)` (`WorldView.update(dt, serverTick)`), doors open while it waits, lamps over the doorways, and a glass door pair across every stop that slides open while the cab is there. It is a handful of meshes, so every tier draws it. `NavGrid` gives every shaft cell a node per stop and joins them with `lift` edges (cost = `liftRideSeconds`, the average wait for the cab plus the ride); any other edge into or out of a cell must be flat. `BotBrain.cabControls` stands the bot in the cab and waits for it; a path that rides two shafts only minds the one it is in. `server/test/nav.test.ts`, `bot-lift.test.ts` and `shared/test/lift.test.ts` pin this. The cab is a safe room on the server: `inLiftCab` (`shared/src/lift.ts`: centre in the shaft and feet on the cab floor, moving or waiting) makes a player unhittable (`recordHistory` and `handleShot` in `Game`, so lag compensation agrees), makes their own shots harmless, and sets `RF_PROTECT` on their snapshot row so others see the protection. ## Ray tracing levels

`RT` in `client/src/game/render/rt-levels.ts` is the table behind the pause menu's **sombra de contato** choice (a `RtChoice`: `auto`, `off`, `light`, `medium`, `high`; default `auto`). A level sets the occlusion target `resolution`, `rays`, `denoiseSamples`, `msaa`, `sceneDepth` (reuse the scene's depth instead of redrawing it for normals), `strength` and `radiusUnits`; `off` is `null` and builds nothing. Only tiers with `QualityProfile.lightRt` run it. To add a level, add it to `RT_LEVELS` and `RT`, keep every knob non-decreasing in cost (`client/test/rt-levels.test.ts` checks it), add a benchmark variant in `RT_VARIANTS` (`client/src/benchmark/options.ts`) and mention it in `README.md`. `auto` runs `AUTO_RT_START` (`high`), or `INTEGRATED_RT_START` (`medium`) when `readGpuFacts` says the card is integrated (`isIntegratedRenderer`: Intel graphics that are not a discrete Arc A or B card, AMD `Radeon Graphics` and `780M` style APUs; `high` costs about 27 ms of GPU per frame on an Intel Arc iGPU), and only then does `RtGovernor` (`rt-governor.ts`) step the running level down once when, over a 3 s stretch, the median frame is over 33 ms (below 30 fps) or more than 5% of frames are over 42 ms (below 24 fps), so a level that holds 30 to 60 fps with a few spikes stays; the client keeps the result as the auto ceiling for the match. A fixed level is never touched by the governor. On an integrated card the first slow-frame hint also says once that the browser may be using it instead of the laptop's discrete card (`INTEGRATED_GPU_TIP`: the Windows graphics setting for the browser). A page cannot choose the card: `powerPreference: "high-performance"` was already requested and Chrome on that laptop still picked the Intel iGPU, which ran the benchmark at 38 fps against 106 fps on the RTX 4070 (measured, same page). Saved settings hold the choice; the old boolean maps to `auto`/`off` in `parseRtChoice`. The occlusion is not blended by `GTAOPass` (its default output copies the whole scene into the write buffer and blends onto it, two extra full-resolution passes over a multisampled half-float target): `GTAOPass.output` is `Off` and `OcclusionOutputPass` (`light-rt.ts`) multiplies the denoised texture into the colour inside the final tone mapping pass, through `withOcclusion`, which throws when three's output shader changes so the game falls back to direct rendering. Measured on an Intel Arc iGPU at 1554 x 1300 (alternating runs, 5 rounds each): `médio` 10.3 to 10.8 ms of GPU per frame before, 6.95 ms after; `leve` 9.7 ms before, 6.4 ms after. Shadow-map size, the vent, fan and spark effects were not changed: they are not the measured limiter.

## Keep the performance tier light

The `desempenho` tier exists for weak machines (integrated graphics, old laptops). Never add a heavy feature to it.

- **Off by default.** A new visual or audio feature that costs frame time, draw calls, fill rate, memory or extra scene passes (post-processing, extra lights or shadows, more particles, bigger render targets, reflections, ray-marched passes) is a column in `QualityProfile` in `client/src/game/render/quality.ts`, on only for the tiers that can afford it, and always `false` or zero for `performance`. Say in a comment which tiers have it, as `fx.sparkle` and `lightRt` do (high only).
- **Not a branch on the tier name.** Read the profile, so the decision stays in the table.
- **Gate it at the source.** The cost must not be paid when the tier is off: do not build the objects, render targets or passes, rather than hiding their output. A feature that needs hardware support (WebGL 2, float targets) also checks the card, and falls back when it throws.
- **Test it.** Add a case next to `only the high tier sparkles` in `client/test/` asserting which tiers have it, so a later change cannot switch it on for `performance`.
- **Cheap is allowed.** Gameplay, sound, text and small effects that cost almost nothing run on every tier, as the impact sounds do. When unsure, measure on the performance tier or leave it off.

- **Agents.** A new MCP tool, a new field in `get_state` or a change in how agents perceive the game goes in `README.md` under "Play with an AI agent (MCP)", in the tool's own `description` (that is what agents read) and in `.claude/skills/play-calindra-strike/SKILL.md`.
